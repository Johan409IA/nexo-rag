- Respuesta obtenida: Según el contexto, el **Teorema CAP** (Brewer, 2000) establece que un sistema distribuido solo puede garantizar 2 de los 3 siguientes elementos:

* **C (Consistency / Consistencia):** Todos los nodos ven los mismos datos al mismo tiempo.
* **A (Availability / Disponibilidad):** El sistema siempre responde (sin error), aunque no sea el dato más reciente.
* **P (Partition Tolerance / Tolerancia a particiones):** El sistema funciona aunque fallen conexiones entre nodos.

### P05 — ¿Qué diferencias principales existen entre los servicios web SOAP y REST?

- Categoría: directa · Curso: Integración de sistemas de información
- Documento esperado: S08_s1 Integración de sistemas de información.pdf · páginas 12
- Respuesta de referencia: SOAP usa su propio protocolo (envelope sobre HTTP/SMTP), solo XML, contrato WSDL obligatorio, seguridad WS-Security y transacciones ACID distribuidas; es más lento y típico en banca, gobierno e integración legacy. REST usa HTTP estándar (GET/POST/PUT/DELETE), admite JSON/XML/HTML, contrato OpenAPI opcional, seguridad OAuth 2.0/JWT/HTTPS, es más rápido y stateless; es el de facto para APIs públicas, mobile y microservicios.
- Respuesta obtenida: Según el contexto proporcionado, las diferencias principales entre SOAP y REST son las siguientes:

* **Protocolo:** SOAP utiliza un protocolo propio (SOAP envelope sobre HTTP/SMTP), mientras que REST utiliza HTTP estándar (GET/POST/PUT/DELETE).
* **Formato de datos:** SOAP utiliza únicamente XML con un envelope SOAP. REST admite JSON, XML, HTML y texto plano.
* **WSDL / Contrato:** En SOAP, el uso de WSDL es obligatorio (contrato formal). En REST, el uso de OpenAPI/Swagger es opcional pero recomendado.
* **Seguridad:** SOAP cuenta con WS-Security nativo (estándar bancario). REST es flexible y utiliza OAuth 2.0, JWT y HTTPS.
* **Transacciones:** SOAP ofrece soporte nativo para ACID distribuido (WS-AtomicTransaction). REST no tiene soporte nativo (es manual).
* **Rendimiento:** SOAP es más lento debido al *overhead* de XML y el envelope. REST es más rápido gracias a un *payload* ligero de JSON.
* **Estado:** SOAP puede ser *Stateful* o *Stateless*. REST es *Stateless* (obligatorio en REST puro).
* **Mejor para:** SOAP se recomienda para banca, gobierno e integración legacy. REST se recomienda para APIs públicas, dispositivos móviles y microservicios.

### P10 — ¿Qué relación tienen la escalabilidad horizontal, el sharding y el teorema CAP?

- Categoría: multi_pagina · Curso: Escalabilidad y big data
- Documento esperado: S07_s1 Escalabilidad y big data.pdf · páginas 8, 9
- Respuesta de referencia: La escalabilidad horizontal (scale-out) añade nodos al clúster y cada nodo gestiona un subconjunto de los datos mediante sharding (particionado por rango de clave, por hash o geográfico). Al distribuir los datos aparecen problemas de consistencia y de JOINs cross-shard, que enmarcan el teorema CAP: en un sistema distribuido solo se garantizan 2 de 3 propiedades (consistencia, disponibilidad y tolerancia a particiones).
- Respuesta obtenida: Con base en el contexto proporcionado, la relación entre estos conceptos es la siguiente:

* **Sharding y Escalabilidad Horizontal:** El sharding (particionado horizontal) consiste en dividir los datos y asignarlos a diferentes nodos o servidores (por ejemplo, mediante métodos como *Range-Based*, *Hash-Based* o *Geographic*). Esto es parte fundamental de la **escalabilidad horizontal** (*Scale-Out*), donde cada nodo gestiona un subconjunto de los datos al añadir más servidores al clúster.
* **Escalabilidad Horizontal y Teorema CAP:** Uno de los problemas o desventajas asociados a la escalabilidad horizontal es la **complejidad de consistencia**, la cual se rige por el **Teorema CAP**. Este teorema establece que en un sistema distribuido (como los que se usan en la escalabilidad horizontal) solo se pueden garantizar 2 de 3 propiedades simultáneamente: Consistencia (C), Disponibilidad (A) y Tolerancia a particiones (P).

- Categoría: multi_pagina · Curso: Integración de sistemas de información
- Documento esperado: S08_s1 Integración de sistemas de información.pdf · páginas 13, 14
- Respuesta de referencia: El uso correcto de los verbos HTTP (GET, POST, PUT, PATCH, DELETE) con sus códigos de estado (200, 201, 204, 400, 401, 403, 404, 409, 429, 500) y unas URLs bien diseñadas (sustantivos en plural, versionado /api/v1 y /api/v2, paginación y filtros como query params, relaciones por sub-recursos), más seguridad (OAuth 2.0 + JWT, API Keys, rate limiting, HTTPS obligatorio) y caché (Cache-Control, ETag).
- Respuesta obtenida: Según el contexto proporcionado, los elementos y mejores prácticas que definen el diseño de una API REST son los siguientes:

* **Principios RESTful, HTTP Verbs y Status Codes:** Uso correcto de los verbos HTTP (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`), los cuales indican la acción (el verbo HTTP define la acción y la URL solo identifica el recurso), y códigos de estado (`Status Codes`).
* **Diseño de URLs RESTful y Mejores Prácticas:**
  * Uso de sustantivos en plural.
  * Versionado de la API (por ejemplo, mediante *URL Path*, *Header* o *Query param*).
  * Inclusión de paginación y filtros como *query params*.
  * Uso de relaciones mediante sub-recursos anidados (máximo 2 niveles).
  * **Prohibiciones:** NO usar verbos en la URL y NO usar camelCase (se prefiere kebab-case).
* **Seguridad y Performance:**
  * OAuth 2.0 + JWT (token Bearer en el header de autorización, con expiración corta y refresh token).
  * API Keys (para acceso server-to-server, rotación periódica y nunca en frontend).
  * Rate Limiting (protección contra abuso, con cabeceras como `X-RateLimit-Limit` y código 429 si se excede).
  * HTTPS obligatorio (TLS 1.3 mínimo, headers HSTS).
  * Cache-Control (para GET idempotentes) y ETag para validación.

### P12 — ¿Por qué se integran los sistemas de información empresariales y qué patrones y middleware se utilizan?

- Categoría: multi_pagina · Curso: Integración de sistemas de información
- Documento esperado: S08_s1 Integración de sistemas de información.pdf · páginas 8, 9, 10
- Respuesta de referencia: La integración (EAI) conecta sistemas heterogéneos (ERP, CRM, RRHH, e-commerce) para compartir datos y procesos en tiempo real, eliminando silos de información y duplicación de datos. Los 4 estilos de integración son: transferencia de archivos, base de datos compartida, invocación remota (RPC/API) y mensajería asíncrona. El middleware típico es el ESB (enrutamiento, transformación, conectores, seguridad centralizada, monitoreo, orquestación), con herramientas como MuleSoft Anypoint, Apache Camel, Azure Integration Services o AWS AppFlow/EventBridge.
- Respuesta obtenida: Basándose estrictamente en el contexto proporcionado:

**¿Por qué se integran los sistemas de información empresariales?**
* Para conectar sistemas de información heterogéneos (ERP, CRM, RRHH, e-commerce, etc.) con el fin de que compartan datos y procesos en tiempo real.
* Para eliminar silos de información y duplicación de datos.
* Para sincronizar datos en tiempo real entre todos los sistemas, eliminando la duplicidad y la entrada manual de datos.
* Para automatizar procesos de negocio end-to-end.
* Para obtener una vista única del cliente/producto/empleado (360°).
* Para reducir costos operativos (hasta un 40% según Gartner, 2023).
* Para tomar decisiones basadas en datos actualizados al segundo, logrando una empresa ágil, con datos confiables y automatización inteligente.
* Para conectar aplicaciones, procesos y datos, facilitando la interoperabilidad y optimizando la gestión empresarial mediante Servicios Web y APIs, lo que fortalece la eficiencia operativa, mejora la toma de decisiones, permite adaptarse a entornos digitales dinámicos e impulsa la innovación y la competitividad.

**¿Qué patrones se utilizan?**
Se utilizan los 4 estilos fundamentales de los *Enterprise Integration Patterns (EIP)*:
1. **Transferencia de archivos:** Un sistema escribe un archivo y otro lo lee en un directorio compartido o por FTP/SFTP.
2. **Base de datos compartida:** Múltiples sistemas leen y escriben en una base de datos central.
3. **Invocación remota (RPC/API):** Un sistema llama directamente a funciones de otro sistema vía red (síncrono: REST, SOAP, gRPC).
4. **Mensajería asíncrona:** Los sistemas se comunican enviando mensajes a través de un broker (cola/topic) para un desacoplamiento total.

**¿Qué middleware se utiliza?**
* **Enterprise Service Bus (ESB):** Middleware de integración que actúa como bus central de comunicación entre aplicaciones heterogéneas, implementando el patrón Hub-and-Spoke.
* **Herramientas de Integración Empresarial específicas mencionadas:**
  * **MuleSoft Anypoint:** iPaaS líder (Salesforce), plataforma API-led connectivity.
  * **Apache Camel:** Open Source — Java, implementa Enterprise Integration Patterns.
  * **Azure Integration Services:** Microsoft Cloud iPaaS (combina Logic Apps, API Management, Service Bus y Event Grid).
  * **AWS AppFlow / EventBridge:** Amazon Cloud iPaaS para flujos de datos seguros e integración basada en eventos.
